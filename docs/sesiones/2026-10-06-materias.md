# Sesión 2026-10-06: Materias (crear y listar)

## Resumen

Primer paso de la fase 1. Ya existe la página protegida **`/materias`**: cada
usuario puede crear materias (solo con el nombre) y ver la lista de las suyas,
ordenada por nombre. La comprobación de sesión vive ahora en un único helper,
`requireUser()` de `lib/session.ts`, que usan `/mazmorra` y todo lo nuevo.
`/mazmorra` y `/materias` se enlazan entre sí. No hubo cambios en la base de
datos.

## Decisiones y por qué

- **Sin cambios en el schema.** La tabla `Subject` (`id`, `name`, `userId`) ya
  tenía todo lo necesario, incluido el índice sobre `userId`.
- **Un helper `requireUser()` en vez de repetir `getSession` + `redirect`.**
  Así cada página o acción protegida usa una sola línea y no se puede olvidar
  la mitad de la comprobación. Va envuelto en `cache` de React para que, en una
  misma petición, la sesión se consulte una sola vez aunque se llame varias.
- **El `userId` sale siempre de la sesión, nunca del formulario.** Cualquiera
  puede mandar un POST a una Server Action con los campos que quiera. Si el
  `userId` viniera del formulario, se podrían crear materias a nombre de otro.
- **Normalizar el nombre antes de validar.** Se quitan los espacios de los
  extremos y se juntan los repetidos de dentro (`"  Cálculo   II "` →
  `"Cálculo II"`). El vacío y el límite de 60 se comprueban **después**. Así,
  `"   "` cuenta como vacío y un nombre de 61 caracteres con un doble espacio
  dentro se acepta, porque normalizado tiene 60.
- **Duplicados comparados en el servidor con `toLocaleLowerCase("es")`, no con
  `mode: "insensitive"` de Prisma.** Prisma traduce ese modo a `ILIKE` de
  Postgres, y en `ILIKE` los caracteres `_` y `%` son comodines: `"Mate_1"`
  chocaría con `"Mate11"`. Se traen los nombres de las materias del usuario y
  se comparan en JavaScript. Decisión de Luis al revisar el plan.
- **El formulario en un Client Component aparte**
  (`nueva-materia-form.tsx`). `useActionState` solo funciona en el navegador,
  pero la página tiene que seguir siendo de servidor para consultar Prisma
  directamente.
- **`revalidatePath("/materias")` para refrescar la lista.** Le dice a Next
  que vuelva a renderizar esa página. Como la llamada se hace dentro de una
  Server Action, la respuesta ya trae la lista nueva en el mismo viaje.
- **Orden en la base (`orderBy: { name: "asc" }`), no en JavaScript.** Al
  planificar existía la duda de que la *collation* de Supabase (las reglas de
  orden del texto) fuera `C`, que pone las mayúsculas antes que las minúsculas.
  La prueba mostró que no: `Álgebra`, `Cálculo II`, `física`, `Zoología` salen
  en orden alfabético normal.
- **Se acepta, por ahora, una carrera en el duplicado.** Ver "Pendientes".

## Archivos nuevos y modificados

Conceptos que ya se explicaron en la [sesión del 5 de

### `lib/session.ts` (nuevo)

```ts
import { cache } from "react";
import { headers } from "next/headers";
import { redirect } from "next/navigation";
import { auth } from "@/lib/auth";
```

- `cache` (de React) memoriza el resultado de una función **durante una sola
  petición**. En la siguiente petición empieza de cero, así que no mezcla
  usuarios.
- `headers` da acceso a las cabeceras de la petición, donde viaja la cookie.
- `redirect` manda al navegador a otra página.
- `auth` es nuestra configuración de Better Auth.

```ts
export const requireUser = cache(async () => {
```

Se define la función y se envuelve en `cache`. Si en el futuro la página y un
componente hijo llaman los dos a `requireUser()`, la base se consulta una sola
vez. Es el patrón que recomienda la guía de autenticación de Next.

```ts
  const session = await auth.api.getSession({ headers: await headers() });
```

Better Auth lee la cookie de las cabeceras y busca la sesión en la tabla
`Session`. Si la cookie no existe, está caducada o es falsa, devuelve `null`.
Es la comprobación segura de la que habla la regla del README: mirar solo si
la cookie existe no basta.

```ts
  if (!session) redirect("/login");

  return session.user;
});
```

Sin sesión, a `/login`. `redirect` lanza un error especial que Next captura,
así que la línea siguiente nunca se ejecuta sin sesión. Por eso TypeScript
sabe que lo que se devuelve siempre es un usuario (con `id`, `name`, `email` y
los campos del personaje: `level`, `souls`, `flame`). Funciona igual en
páginas y en Server Actions.

### `app/materias/actions.ts` (nuevo)

```ts
"use server";
```

Todas las funciones exportadas de este archivo son Server Actions: se ejecutan
en el servidor aunque las llame un formulario del navegador.

```ts
import { revalidatePath } from "next/cache";
import { prisma } from "@/lib/prisma";
import { requireUser } from "@/lib/session";
import type { EstadoFormulario } from "@/app/registro/actions";

const MAX_LONGITUD_NOMBRE = 60;
```

Se reutiliza el tipo `EstadoFormulario` (`{ error: string | null }`) de
registro, para que todos los formularios hablen el mismo idioma. El límite va
en una constante para no repetir el 60 en la comprobación y en el mensaje.

```ts
export async function crearMateria(
  _estadoAnterior: EstadoFormulario,
  formData: FormData,
): Promise<EstadoFormulario> {
  const user = await requireUser();
```

La firma es la que exige `useActionState`. Lo primero es la sesión: si alguien
llama a la acción sin sesión (por ejemplo, con un POST hecho a mano), se le
redirige a `/login` y no se toca la base. **El dueño de la materia sale de
aquí, no del formulario.**

```ts
  const name = String(formData.get("name") ?? "")
    .trim()
    .replace(/\s+/g, " ");
```

- `formData.get("name") ?? ""`: si el campo no viene, cadena vacía.
- `String(...)`: `formData.get` puede devolver un archivo. Esto lo fuerza a
  texto.
- `.trim()`: quita los espacios del principio y del final.
- `.replace(/\s+/g, " ")`: `\s+` significa "uno o más espacios en blanco
  seguidos" (también tabuladores), y la `g` hace que se aplique a todo el
  texto. Cada grupo se sustituye por un solo espacio.

```ts
  if (name === "") return { error: "Escribe un nombre para la materia." };
  if (name.length > MAX_LONGITUD_NOMBRE) {
    return { error: `El nombre no puede pasar de ${MAX_LONGITUD_NOMBRE} caracteres.` };
  }
```

Validaciones **después** de normalizar. El `maxLength` del input es solo una
ayuda en el navegador y se puede saltar. Esta comprobación es la que de verdad
protege.

```ts
  const existentes = await prisma.subject.findMany({
    where: { userId: user.id },
    select: { name: true },
  });
```

Trae solo la columna `name` de las materias **de este usuario**. El filtro por
`userId` hace que dos usuarios distintos sí puedan tener una materia con el
mismo nombre.

```ts
  const nombreNormalizado = name.toLocaleLowerCase("es");
  const repetida = existentes.some(
    (materia) => materia.name.toLocaleLowerCase("es") === nombreNormalizado,
  );
  if (repetida) return { error: `Ya tienes una materia llamada "${name}".` };
```

Pasa los dos nombres a minúsculas con las reglas del español y los compara
como texto exacto, sin comodines. `.some(...)` devuelve `true` en cuanto
encuentra una coincidencia. Ojo: las tildes sí cuentan, así que `"calculo"` y
`"cálculo"` son nombres distintos.

```ts
  await prisma.subject.create({ data: { name, userId: user.id } });

  revalidatePath("/materias");
  return { error: null };
}
```

Crea la fila y pide a Next que vuelva a renderizar `/materias`, de modo que la
lista se actualiza sin recargar. `{ error: null }` le dice al formulario que
todo fue bien.

### `app/materias/nueva-materia-form.tsx` (nuevo)

```tsx
"use client";

import { useActionState } from "react";
import { crearMateria } from "./actions";
import type { EstadoFormulario } from "@/app/registro/actions";

const estadoInicial: EstadoFormulario = { error: null };
```

Es un componente de cliente porque usa un hook (`useActionState`). Importa la
Server Action del archivo de al lado. Next la convierte en una llamada al
servidor: el código de la acción nunca llega al navegador.

```tsx
export function NuevaMateriaForm() {
  const [estado, accion, enviando] = useActionState(crearMateria, estadoInicial);
```

Igual que en login y registro: `estado` guarda lo último que devolvió la
acción, `accion` es lo que se pasa al `<form>` y `enviando` vale `true`
mientras se espera la respuesta.

```tsx
  return (
    <>
      <form action={accion}>
        <label htmlFor="name">Nueva materia</label>
        <input id="name" name="name" type="text" maxLength={60} required />

        <button type="submit" disabled={enviando}>
          {enviando ? "Creando..." : "Crear"}
        </button>
      </form>
      {estado.error && <p role="alert">{estado.error}</p>}
    </>
  );
}
```

- `<>...</>` (fragmento): agrupa el formulario y el mensaje sin añadir una
  etiqueta extra.
- `name="name"` es la clave con la que la acción lee el campo.
- `maxLength={60}` y `required` son ayudas del navegador. La validación real
  está en el servidor. `required` no impide enviar solo espacios: por eso el
  servidor comprueba el vacío después de normalizar.
- El botón se desactiva mientras se envía, para evitar dobles clics.
- `role="alert"` hace que los lectores de pantalla lean el error en voz alta.

### `app/materias/page.tsx` (nuevo)

```tsx
import Link from "next/link";
import { prisma } from "@/lib/prisma";
import { requireUser } from "@/lib/session";
import { NuevaMateriaForm } from "./nueva-materia-form";

export default async function MateriasPage() {
  const user = await requireUser();
```

Es un Server Component (no lleva `"use client"`), así que puede ser `async` y
hablar con Prisma directamente. Lo primero es la sesión: sin ella, a `/login`.

```tsx
  const subjects = await prisma.subject.findMany({
    where: { userId: user.id },
    orderBy: { name: "asc" },
    select: { id: true, name: true },
  });
```

Solo las materias de este usuario (`where`), de la A a la Z (`asc`), y solo
las columnas que se muestran (`select`). Pedir solo lo necesario es una buena
costumbre: si mañana `Subject` tiene más columnas, no viajan sin motivo.

```tsx
  return (
    <main>
      <h1>Mis materias</h1>
      <NuevaMateriaForm />
      {subjects.length === 0 ? (
        <p>Todavía no tienes materias. Crea la primera con el formulario.</p>
      ) : (
        <ul>
          {subjects.map((subject) => (
            <li key={subject.id}>{subject.name}</li>
          ))}
        </ul>
      )}
      <p>
        <Link href="/mazmorra">Volver a la mazmorra</Link>
      </p>
    </main>
  );
}
```

- `condición ? A : B`: si no hay materias, el mensaje. Si las hay, la lista.
- `.map(...)` convierte cada materia en un `<li>`. `key={subject.id}` le sirve
  a React para saber qué elemento es cuál cuando la lista cambia. El `id` es
  único, así que es la clave ideal.
- El enlace de vuelta usa `Link`, igual que el resto de la app.

## Pendientes

- **Índice único sobre `(userId, lower(name))` en `Subject`.** La comprobación
  de duplicados lee y después escribe. Si llegan dos envíos casi a la vez, los
  dos pueden pasar la comprobación y crear la misma materia dos veces. Solo un
  índice único en la base lo impide del todo. Prisma no sabe declarar un
  índice sobre `lower(name)` en el schema, así que hará falta una migración
  con SQL escrito a mano (`migrate dev --create-only` y añadir
  `CREATE UNIQUE INDEX ... ON "Subject" ("userId", lower("name"))`). Antes
  habría que revisar que no existan duplicados. Ojo: `lower()` de Postgres y
  `toLocaleLowerCase("es")` pueden no coincidir en casos raros.
- Que el formulario conserve lo escrito cuando hay error.
