# Sesión 2026-10-07: La batalla (vigilias de estudio)

## Resumen

Cada jefe ya se puede combatir en `/mazmorra/batalla/[id]`. Se combate con
**vigilias** de 25 minutos: al comenzar, el servidor fija la hora de inicio y
la de fin; al llegar a cero aparece "Asestar golpe", y cada golpe le quita 100
de vida al jefe. Al llegar a 0, el jefe pasa a `DEFEATED` y se ve la victoria.
La escena es la ilustración del jefe (`public/jefes/*.webp`), con respiración
lenta, tajo, sacudida, destello y "−100" hechos solo con CSS.

La base garantiza dos cosas aunque el código fallara:

- una sola vigilia abierta por usuario, con un **índice único parcial**;
- un único golpe por vigilia, con una **actualización condicional dentro de
  una transacción**.

Además, la mazmorra muestra la miniatura de cada jefe y el enlace "Atacar",
y la landing ya no dice "Próximamente" en "Combate real".

Sigue a la [sesión de diseño de la mazmorra](2026-10-07-diseno-mazmorra-materias.md),
que creó `HpBar`, `SpriteSlot` y las consultas de contenedor.

## Decisiones y por qué

- **Bestiario cerrado en `lib/game.ts`, con la clave del jefe guardada en
  `Task.bossKey`.** La clave es también el nombre del archivo
  (`public/jefes/<clave>.webp`). El servidor elige el jefe al azar al
  invocar; el formulario nunca lo envía.
- **`bossKey` es opcional (`String?`) y se lee siempre con `bossForTask()`.**
  Producción y desarrollo comparten la base, y hasta el push sigue corriendo
  el código viejo, que crea tareas sin ese campo. Si la columna fuera
  obligatoria, el código viejo fallaría al invocar.
  - La migración rellenó las 4 tareas existentes con una regla determinista
    dentro de su dificultad: el código del último carácter del id, módulo 2.
  - `bossForTask()` usa **la misma regla y la misma lista**, así que una
    tarea que llegue sin clave muestra el mismo jefe que le habría dado el
    relleno.
  - Se comprobó con el `bossForTask()` real: las 4 tareas coinciden.
- **"Una sola vigilia abierta por usuario" con un índice único parcial**
  (propuesta de Luis): `UNIQUE ("userId") WHERE "completedAt" IS NULL`.
  - Exigió guardar `userId` en `StudySession`, porque `Task` no lo tiene.
  - **Plan B descartado:** una columna `openUserId String? @unique` con un
    `CHECK`. Habría quedado entera en el schema, pero guarda el mismo dato
    dos veces. Solo hacía falta si Prisma intentaba borrar el índice
    parcial, y no lo hace (ver "Base de datos").
- **El reloj lo cuenta el servidor.** `startedAt` y `endsAt` se fijan al
  comenzar con la hora de Node. El navegador no resta 1 a un contador: en
  cada tic recalcula lo que falta a partir de `endsAt` y de la diferencia
  entre su reloj y el del servidor (`serverNow`).
  - Así no se desajusta con la pestaña en segundo plano ni con un reloj
    local mal puesto.
  - El error de esa diferencia solo puede **retrasar** el cero (incluye lo
    que tardó la página en llegar), nunca adelantarlo. Por eso la interfaz
    nunca pide un golpe que el servidor vaya a rechazar.
- **Orden de bloqueos (ajuste de Luis).** `comenzarVigilia` y `asestarGolpe`
  empiezan con el mismo `SELECT … FROM "Task" … FOR UPDATE` y solo después
  tocan la vigilia. Si cada una bloqueara en un orden distinto, un golpe y un
  comienzo simultáneos podrían quedarse esperando el uno al otro para
  siempre (interbloqueo).
- **Abandonar solo borra si la vigilia aún no terminó.** Una vigilia
  cumplida ya se ganó su golpe, y un clic tardío desde otra pestaña no debe
  tirarlo.
- **Acciones con `refresh()` y sin `revalidatePath("/mazmorra")`** (ajuste d).
  Se comprobó en la build de producción: después de un golpe, volver con el
  botón atrás muestra la vida nueva desde el primer pintado. Las páginas
  dinámicas no se guardan en la caché del cliente en Next 16
  (`02-guides/prefetching.md`: "Dynamic page … Client Cache TTL: Off").
- **Banda de vida apilada arriba a la izquierda, con 40 % de ancho como
  máximo** (decisión 1 de Luis).
  - En Figma la barra cruzaba el centro, justo encima del casco del
    caballero hueco (empieza al ~6 % de la altura) y de la corona del liche
    (al ~9 %).
  - En las seis ilustraciones la esquina superior izquierda no tiene ninguna
    cabeza.
  - Solo se oscurece esa esquina, con un degradado radial de `night` a
    transparente.
- **Botón "Pausar movimiento"** (decisión 2), por la regla del proyecto y
  WCAG 2.2.2. Es un botón de 44 px con `aria-pressed` en la barra superior;
  la elección se recuerda en `localStorage`. No aparece con movimiento
  reducido ni en la victoria, porque ahí no hay nada que pausar.
- **El cliente recibe la duración como prop** (ajuste c). La variable de
  prueba solo existe en el servidor.
- **`SpriteSlot` se borró.** Su único uso era la tarjeta de jefe, que ahora
  muestra la miniatura real.
- **Aviso de "otra vigilia abierta" como texto, no como `Alert`.** No es un
  error, y `role="alert"` se anunciaría nada más cargar. `Alert` queda para
  los rechazos de las acciones.

## Base de datos

### Migración `20261007210121_batalla`

```sql
ALTER TABLE "StudySession" ADD COLUMN "completedAt" TIMESTAMP(3),
ADD COLUMN "endsAt" TIMESTAMP(3) NOT NULL,
ADD COLUMN "userId" TEXT NOT NULL;
ALTER TABLE "Task" ADD COLUMN "bossKey" TEXT;
CREATE INDEX "StudySession_userId_idx" ON "StudySession"("userId");
ALTER TABLE "StudySession" ADD CONSTRAINT "StudySession_userId_fkey"
  FOREIGN KEY ("userId") REFERENCES "User"("id") ON DELETE CASCADE ON UPDATE CASCADE;
```

Esto lo generó Prisma a partir del schema.

- **Las columnas `NOT NULL` sin valor por defecto son seguras aquí:**
  `StudySession` tenía 0 filas y el código viejo no escribe en ella. Con
  filas, Postgres habría rechazado la migración.
- **`userId` lleva su índice normal** para que borrar un usuario (la cascada)
  no recorra toda la tabla. El índice parcial solo cubre las vigilias
  abiertas.

```sql
UPDATE "Task" SET "bossKey" = (CASE "difficulty"
    WHEN 'EASY'   THEN ARRAY['centinela-de-huesos', 'rata-de-las-cloacas']
    WHEN 'MEDIUM' THEN ARRAY['ogro-de-las-ruinas', 'caballero-hueco']
    WHEN 'HARD'   THEN ARRAY['dragon-de-la-caverna', 'liche-del-osario']
  END)[1 + ascii(right("id", 1)) % 2]
WHERE "bossKey" IS NULL;
```

Este relleno se escribió a mano.

- `right("id", 1)` es el último carácter del id; `ascii()` da su código.
- `% 2` elige una de las dos opciones. El `1 +` está porque los arrays de
  Postgres empiezan en 1, no en 0.
- Es la misma cuenta que `id.charCodeAt(id.length - 1) % 2` en JavaScript.

```sql
CREATE UNIQUE INDEX "StudySession_userId_open_key"
  ON "StudySession"("userId") WHERE "completedAt" IS NULL;
```

**Índice único parcial,** también escrito a mano.

- Un índice único normal impediría que un usuario tuviera dos vigilias,
  incluso cumplidas.
- El `WHERE` hace que el índice solo contenga las filas que cumplen la
  condición, las abiertas. Dos vigilias abiertas del mismo usuario chocan;
  las cumplidas no cuentan.
- Al cerrar una vigilia (rellenar `completedAt`), su fila **sale** del índice
  y deja sitio a la siguiente.

**¿Prisma lo borra en la siguiente migración?** No.

- Prisma 6.19.3 no tiene la opción `partialIndexes` (se buscó en el
  paquete), así que el índice no puede estar en `schema.prisma`.
- Para comprobar si Prisma intentaría borrarlo, se repitieron todas las
  migraciones (la nueva incluida) en una base temporal y se comparó el
  resultado con el schema. El diff salió **vacío**
  (`-- This is an empty migration.`).
- **Prueba de control:** con una copia del schema sin `@@index([userId])`,
  el mismo diff sí generó `DROP INDEX "StudySession_userId_idx"`. Eso
  demuestra que la base temporal tenía la migración nueva y que el diff
  detecta índices de más. El índice parcial no apareció en ninguno de los
  dos: Prisma lo ignora.

**RLS:** no hay tablas nuevas, así que no hace falta migración de RLS.

### `lib/game.ts` (modificado: vigilias y bestiario)

```ts
export const VIGIL_MINUTES = 25;

export function vigilDurationMs(): number {
  if (process.env.NODE_ENV !== "production") {
    const testSeconds = Number(process.env.EMBER_TEST_VIGIL_SECONDS);
    if (Number.isInteger(testSeconds) && testSeconds > 0) return testSeconds * 1000;
  }
  return VIGIL_MINUTES * 60 * 1000;
}
```

- `VIGIL_MINUTES` es la regla del juego; `vigilDurationMs()` es lo que de
  verdad dura una vigilia, en milisegundos (la unidad de `Date`).
- `Number(undefined)` da `NaN`, y `Number.isInteger(NaN)` es `false`: si la
  variable no está, o es basura como `"abc"` o `"-5"`, se usan los 25
  minutos.
- La comprobación de `NODE_ENV` va primero para que en producción ni
  siquiera se lea la variable. Olvidarla puesta en Vercel no hace trampas.

```ts
export type BossKey = "centinela-de-huesos" | "rata-de-las-cloacas" | … ;
export type Boss = { key: BossKey; name: string; thumbPosition: string };
export const BESTIARY: Record<BossKey, Boss> = { … };
```

- **`BossKey` es un tipo unión:** solo admite esas seis cadenas, y TypeScript
  avisa si escribes mal una clave.
- `Record<BossKey, Boss>` obliga a que el bestiario tenga **exactamente** una
  entrada por clave.
- `thumbPosition` es el `object-position` de la miniatura (por ejemplo,
  `"50% 10%"` para el caballero). La miniatura recorta arriba y abajo, y
  este valor elige qué franja se ve para que no se corte la cabeza.

```ts
export const BOSSES_BY_DIFFICULTY: Record<Difficulty, readonly BossKey[]> = {
  EASY: ["centinela-de-huesos", "rata-de-las-cloacas"], … };
```

Los jefes de cada dificultad. **El orden importa:** la migración usa la misma
lista. `readonly` impide modificarla por error, por ejemplo con `push`.

```ts
export function randomBossFor(difficulty: Difficulty): BossKey {
  const options = BOSSES_BY_DIFFICULTY[difficulty];
  return options[Math.floor(Math.random() * options.length)];
}
```

- `Math.random()` da un número entre 0 (incluido) y 1 (sin incluir).
- Multiplicado por 2 y redondeado hacia abajo da 0 o 1: el índice de una de
  las dos opciones.

```ts
export function bossForTask(task: { id: string; difficulty: Difficulty; bossKey: string | null }): Boss {
  const options = BOSSES_BY_DIFFICULTY[task.difficulty];
  const saved = options.find((key) => key === task.bossKey);
  if (saved) return BESTIARY[saved];
  const index = task.id.charCodeAt(task.id.length - 1) % options.length;
  return BESTIARY[options[index]];
}
```

- **Es la única puerta para saber el jefe de una tarea.**
- Primero busca la clave guardada **dentro de las de su dificultad**: una
  clave rara o de otra dificultad se ignora, en vez de mostrar un dragón en
  un jefe fácil.
- Si no hay clave válida, usa la regla determinista. Determinista significa
  que con el mismo id siempre sale el mismo jefe, en cada visita.

`bossImageSrc(key)` devuelve `/jefes/<clave>.webp`, la ruta pública.

### `app/mazmorra/batalla/[id]/countdown.ts` (nuevo)

```ts
export function formatCountdown(ms: number): string {
  const totalSeconds = Math.max(0, Math.ceil(ms / 1000));
  const minutes = Math.floor(totalSeconds / 60);
  const seconds = totalSeconds % 60;
  return `${String(minutes).padStart(2, "0")}:${String(seconds).padStart(2, "0")}`;
}
```

- Convierte milisegundos en `mm:ss`.
- **`Math.ceil` redondea hacia arriba:** con 24 min 59,4 s por delante se lee
  `25:00`, y `00:00` solo aparece cuando de verdad llegó la hora de fin. Con
  `Math.floor` se vería `00:00` casi un segundo antes de que el servidor
  aceptara el golpe.
- `Math.max(0, …)` evita `-0:01` si el tic llega tarde.
- `padStart(2, "0")` rellena con un cero a la izquierda: `5` → `05`.
- Va en su propio archivo porque lo usan el servidor (en el mensaje "faltan
  mm:ss") y el navegador. Un archivo `"use server"` solo puede exportar
  funciones asíncronas.

### `app/mazmorra/batalla/[id]/actions.ts` (nuevo)

```ts
"use server";
```

Todas las funciones exportadas son Server Actions: el navegador las llama por
un POST. **Cualquiera puede hacer ese POST a mano**, así que cada una
comprueba todo desde cero.

```ts
export type ResultadoBatalla =
  | { ok: true; currentHp?: number; defeated?: boolean }
  | { ok: false; error: string };
```

- Es una **unión discriminada**: según el valor de `ok`, TypeScript sabe qué
  otros campos hay. Si `result.ok` es `false`, `result.error` existe.
- Los tipos sí se pueden exportar desde un archivo `"use server"`, porque
  desaparecen al compilar.

```ts
async function tareaPropia(taskId: unknown, userId: string) {
  if (typeof taskId !== "string") notFound();
  const task = await prisma.task.findFirst({ where: { id: taskId, subject: { userId } }, select: { id: true } });
  if (!task) notFound();
  return task;
}
```

- `taskId: unknown`: aunque TypeScript diga `string`, por el POST puede
  llegar cualquier cosa (en las pruebas se mandó el número `12345`).
- `notFound()` lanza un error especial que Next convierte en un 404. Se usa
  el mismo 404 si la tarea no existe o si es de otro usuario, para no
  revelar qué ids existen.
- `subject: { userId }` es la forma de filtrar por dueño, porque `Task` no
  tiene `userId`.

```ts
async function bloquearTarea(tx: Prisma.TransactionClient, taskId: string) {
  const rows = await tx.$queryRaw<{ status: TaskStatus }[]>`
    SELECT "status" FROM "Task" WHERE "id" = ${taskId} FOR UPDATE`;
  return rows[0]?.status;
}
```

- **Transacción:** un grupo de operaciones que se aplica entero o no se
  aplica. `tx` es el cliente de Prisma dentro de esa transacción.
- **`FOR UPDATE`** bloquea la fila de la tarea hasta que la transacción
  termina. Otra transacción que quiera bloquear la misma fila **espera su
  turno**. Así, un golpe y un comienzo contra el mismo jefe se ponen en fila
  en vez de pisarse.
- **`$queryRaw` con plantilla** (las comillas invertidas): `${taskId}` no se
  pega al texto del SQL. Viaja aparte, como parámetro, así que un id
  malicioso no puede inyectar SQL. **Nunca `$queryRawUnsafe`.**
- Prisma no tiene `FOR UPDATE` en su API normal; por eso es SQL a mano.

```ts
export async function comenzarVigilia(taskId: string) {
  const user = await requireUser();
  const task = await tareaPropia(taskId, user.id);
  const now = new Date();
  const durationMs = vigilDurationMs();
  const endsAt = new Date(now.getTime() + durationMs);
```

- `requireUser()` va primero: sin sesión, redirige a `/login`.
- Inicio y fin salen del reloj del servidor. `getTime()` da milisegundos
  desde 1970, y sumar la duración da la hora de fin.

```ts
    resultado = await prisma.$transaction(async (tx) => {
      const status = await bloquearTarea(tx, task.id);
      if (status !== "ALIVE") return fallo("Este jefe ya ha caído.");
      await tx.studySession.create({ data: { taskId: task.id, userId: user.id, startedAt: now, endsAt,
        durationMinutes: Math.ceil(durationMs / 60_000) } });
      return { ok: true } as const;
    });
```

- **Transacción interactiva:** Prisma abre la transacción, ejecuta la
  función y hace COMMIT al terminar, o ROLLBACK (deshacer) si lanza un
  error.
- **Primero la tarea, después la vigilia** (el mismo orden que el golpe).
  Si a la vez se está dando el golpe final, el bloqueo espera; al pasar, ve
  `DEFEATED` y no crea una vigilia contra un jefe muerto. Esto se probó.
- `durationMinutes` redondea hacia arriba: una vigilia de prueba de 45 s
  cuenta como 1 minuto en el resumen de la victoria.

```ts
  } catch (error) {
    if (error instanceof Prisma.PrismaClientKnownRequestError && error.code === "P2002") {
      resultado = fallo("Ya tienes una vigilia en curso. …");
    } else throw error;
  }
  refresh();
  return resultado;
```

- **`P2002`** es el código de Prisma para "choca con un índice único". Aquí
  solo puede ser el índice parcial, porque ya hay otra vigilia abierta. **Es
  la base, no el código, la que impide la segunda.**
- Cualquier otro error se relanza: no se oculta un fallo inesperado.
- **`refresh()`** (de `next/cache`, solo dentro de Server Actions) hace que
  la misma respuesta traiga la página vuelta a pintar, con los datos nuevos.

```ts
export async function abandonarVigilia(taskId: string) {
  …
  const { count } = await prisma.studySession.deleteMany({
    where: { taskId: task.id, userId: user.id, completedAt: null, endsAt: { gt: now } },

```

- `deleteMany` borra lo que cumpla la condición y dice cuántas filas
  (`count`).
- `endsAt: { gt: now }` (*greater than*, mayor que): solo si aún no
  terminó.
- Si `count` es 0, busca la vigilia abierta para dar el mensaje correcto:
  "ya terminó: asesta el golpe" o "no tienes ninguna vigilia en curso".

```ts
export async function asestarGolpe(taskId: string) {
  …
  const resultado = await prisma.$transaction(async (tx) => {
    const status = await bloquearTarea(tx, task.id);
    if (status !== "ALIVE") return fallo("Este jefe ya ha caído.");
    const { count } = await tx.studySession.updateMany({
      where: { taskId: task.id, userId: user.id, completedAt: null, endsAt: { lte: now } },
      data: { completedAt: now },
    });
```

- **Actualización condicional:** la vigilia se cierra **solo si** es de este
  usuario y de esta tarea, sigue abierta y su hora de fin ya pasó
  (`lte` = menor o igual).
- **Esto evita el doble golpe:** si dos pestañas golpean a la vez, la
  segunda espera el bloqueo y, al pasar, la vigilia ya tiene `completedAt`,
  así que `count` es 0. Se probó: una devolvió `ok` y la otra el mensaje
  "Puede que ya asestaras el golpe en otra pestaña".
- Si `count` es 0, se busca la causa: "La vigilia aún no ha terminado:
  faltan 00:30" o "No hay ninguna vigilia que golpear".

```ts
    const golpeada = await tx.task.update({
      where: { id: task.id },
      data: { currentHp: { decrement: HP_PER_BLOCK } },
      select: { currentHp: true },
    });
    if (golpeada.currentHp <= 0) {
      await tx.task.update({ where: { id: task.id }, data: { currentHp: 0, status: "DEFEATED" } });
      return { ok: true, currentHp: 0, defeated: true };
    }
```

- `decrement` resta dentro de la base (`SET "currentHp" = "currentHp" - 100`),
  sin leer y escribir por separado.
- Si queda en 0 o menos, se fija en 0 y el jefe pasa a `DEFEATED`. Todo va
  en la misma transacción, así que nadie llega a ver una vida negativa.

## Errores y lecciones

- **El foco se iba a `<body>` al pulsar "Comenzar".** El botón pasaba a
  `disabled` mientras esperaba, y un elemento con el foco que se desactiva
  lo pierde. **Lección:** mientras se espera una respuesta, `aria-disabled`
  y no hacer nada en el clic; `disabled` solo para lo que de verdad no se
  puede usar.
- **`react-hooks/purity`: "Cannot call impure function during render"** por

  `loadBattle()`, fuera del componente.
- **La pausa no paraba nada.** `aria-pressed` y `localStorage` iban bien,
  pero `getAnimations()` decía `drift=running`. El atajo `animation:` de
  `motion-safe:animate-drift` está dentro de un `@media` que Tailwind

  cambiar una sola propiedad de una animación declarada con atajo, estilo
  en línea (`style={{ animationPlayState: "paused" }}`), que gana a
  cualquier clase.
- **Contraste justo en un caso.** Se recompuso en un canvas cada
  ilustración con la viñeta y el degradado y se midió el contraste WCAG de
  cada texto contra los píxeles de detrás. El liche a 768 px con un nombre
  de dos líneas daba 4,6:1 en la criatura dorada. Con `via-night/75` (antes

## Conceptos de esta sesión

- **Transacción:** un grupo de operaciones sobre la base que se aplica
  entero (COMMIT) o no se aplica (ROLLBACK). Nadie ve los pasos intermedios.
- **Bloqueo de fila (`SELECT … FOR UPDATE`):** reserva una fila hasta el
  final de la transacción. Otra transacción que quiera bloquearla espera su
  turno.
- **Carrera (*race condition*):** dos peticiones casi simultáneas que leen el
  mismo estado y actúan las dos, como dos golpes por una sola vigilia.
- **Interbloqueo (*deadlock*):** A espera a B y B espera a A. Postgres lo
  detecta y cancela una, pero es un error. Se evita bloqueando siempre en el
  mismo orden.
- **Actualización condicional:** un `UPDATE … WHERE <condición>` que solo
  cambia la fila si la condición sigue siendo cierta en ese momento. Prisma
  dice cuántas filas cambió (`count`).
- **Índice único parcial:** un índice único que solo incluye las filas que
  cumplen un `WHERE`, como las vigilias abiertas.
- **`P2002`:** el código de error de Prisma cuando una escritura choca con un
  índice único.
- **Consulta parametrizada:** el SQL y los valores viajan por separado, así
  que un valor nunca se interpreta como SQL (inyección).
- **Determinista:** con la misma entrada, siempre el mismo resultado.
- **Desviación de reloj (*offset*):** la diferencia entre el reloj del
  servidor y el del ordenador del usuario.
- **Hidratación:** cuando React toma el HTML que mandó el servidor y le añade
  la interactividad. Si el primer pintado del navegador no coincide con ese
  HTML, React avisa (desajuste de hidratación).
- **`useTransition`:** marca una actualización como "en segundo plano" y da
  `pending` mientras dura.
- **`useSyncExternalStore`:** lee un valor que vive fuera de React (aquí,
  `localStorage`), con un valor aparte para el servidor y la hidratación.
- **`useRef`:** una caja que conserva un valor entre pintados sin provocar
  otro pintado; también apunta a un elemento del DOM.
- **Región viva (`role="status"`):** el lector de pantalla lee lo que cambia
  dentro sin mover el foco. `role="timer"` es lo contrario: no se anuncia
  solo.
- **`aria-pressed`:** convierte un botón en un interruptor (pulsado o no)
  para el lector de pantalla.
- **`@keyframes`:** los pasos de una animación CSS. `animation-fill-mode:
  forwards` hace que el elemento se quede en el último paso.
- **`prefers-reduced-motion`:** el ajuste del sistema "reducir movimiento".
  `motion-safe:` aplica una clase solo si el usuario **no** lo pidió.
- **LCP (*Largest Contentful Paint*):** cuándo se pinta lo más grande de la
  página al cargar; se mide para saber si la página "parece" cargada pronto.
- **`next/image` con `fill` y `sizes`:** la imagen llena su contenedor
  (que debe tener `position: relative`), y `sizes` le dice al navegador
  cuánto ocupará para que elija el archivo del tamaño justo.

## Para retomar en otro equipo

1. `git pull` y `npm install` (`postinstall` ejecuta `prisma generate`).
2. No hace falta ninguna variable nueva en `.env`.
3. `npx prisma migrate status` debe decir que la base está al día: la
   migración `20261007210121_batalla` ya está aplicada en la base
   compartida.
4. Para probar sin esperar 25 minutos:
   `EMBER_TEST_VIGIL_SECONDS=45 npm run dev` (Git Bash), o en PowerShell
   `$env:EMBER_TEST_VIGIL_SECONDS='45'; npm run dev`.
