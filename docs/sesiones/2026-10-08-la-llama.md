# Sesión 2026-10-08: La llama (racha diaria)

## Resumen

El personaje tiene ahora **llama**: los días seguidos en los que ha asestado
al menos un golpe. Se ve a la derecha del nombre, en el bloque del personaje
de todas las páginas con `AppShell`, en tres estados: **encendida** (golpeó
hoy), **en peligro** (golpeó ayer, hoy todavía no) y **apagada** (antes de
ayer o nunca, con un 0 gris). Si la llama se apaga después de haber tenido
racha, debajo de la cabecera sale el aviso "La llama se ha extinguido. Golpea
hoy para volver a encenderla.", que desaparece al volver a golpear. Los días
se cuentan en hora de Colombia, igual que las fechas de entrega.

La landing ya no marca "La llama" como "Próximamente".

Diseño: Figma `zVFMRb61utFXGTcSX0sYSG`, marcos 99:2 (mazmorra de
escritorio), 99:165 (móvil) y 99:313 (los tres estados y los avisos). La
tarjeta "Misión de redención" de 99:2 y 99:165 y los avisos de almas
recuperadas o perdidas de 99:313 son del paso siguiente y no se hicieron.

## Decisiones y por qué

- **Se guarda la racha (`User.flame`) y el día del último golpe
  (`User.lastStrikeDay`); el estado se deduce al leer.** Cargar una página no
  escribe nada en la base: si la llama de alguien se apaga, `flame` sigue
  guardando su racha antigua (por eso se sabe que hay que enseñar el aviso)
  hasta que vuelva a golpear. La alternativa, "apagar" la racha en la base al
  entrar, convertiría cada visita en una escritura y abriría carreras entre
  pestañas.
- **El día del último golpe sigue la convención de `dueDate`:** el día de
  Colombia guardado a las 00:00 UTC. Así la resta "hoy − último golpe" da
  días enteros y el servidor (Vercel, en UTC) no se equivoca de día. Ver
  [la sesión de invocar jefes](2026-10-06-invocar-jefes.md), donde se fijó
  esa convención.
- **Las reglas son dos funciones puras en `lib/game.ts`** (`flameState` y
  `flameAfterStrike`) que reciben "hoy" como parámetro. Una *función pura*
  da siempre el mismo resultado con los mismos datos y no lee el reloj ni la
  base, así que se puede probar con cualquier día sin esperar a que llegue.
- **Al golpear, el usuario se bloquea con `SELECT … FOR UPDATE`
  (`bloquearUsuario`), igual que la tarea.** Antes se sumaban las almas con
  `increment` (la base suma sola) y no hacía falta leer la fila. Ahora la
  llama necesita leer `flame` y `lastStrikeDay` antes de escribir, y en el
  paso siguiente (redención) se quitarán y devolverán almas. Con la fila
  bloqueada, leer, calcular en el código y escribir una vez es seguro. Luis
  eligió esta opción. Se descartó leer la llama del `user` de
  `requireUser()`: no añadía viajes a la base, pero era leer fuera del
  bloqueo.
  - **Coste:** el golpe hace siempre dos viajes para el usuario (bloquear y
    escribir). Antes era uno, o dos si se subía de nivel. Como contrapartida
    desaparece la segunda escritura del nivel: ahora todo va en una.
- **`flame` se calcula una vez en `AppShell`** y se pasa a los dos bloques del
  personaje (escritorio y móvil) y al aviso, para que no puedan dar dos "hoy"
  distintos.
- **El aviso no lleva `role="alert"`:** no es un error y ya está en la página
  al cargarla (`role="alert"` es para lo que aparece de repente).
- **La llama es `role="img"` con `aria-label`.** Un `aria-label` en un
  elemento sin rol no lo leen bien todos los lectores de pantalla; con
  `role="img"` se lee la frase completa ("Racha: 5 días. Encendida.") en vez
  de "5" suelto.
- **El aviso se parte en varias líneas en móvil.** El Figma lo dibuja en una
  sola (`nowrap`), pero a 320 px se saldría de la pantalla.

## Archivos nuevos y modificados

### `lib/game.ts` (modificado: la llama)

```ts
import { parseDateInput } from "@/lib/dates";
```

`parseDateInput` convierte `"2026-10-08"` en un `Date` a las 00:00 UTC de ese
día (ya existía para las fechas de entrega). `lib/dates.ts` no importa nada
del servidor, así que `game.ts` sigue pudiéndose usar en el navegador.

```ts
const DAY_MS = 24 * 60 * 60 * 1000;
```

Los milisegundos de un día, para pasar una resta de fechas a días.

```ts
function parseToday(today: string): Date {
  const date = parseDateInput(today);
  if (!date) throw new Error(`Día no válido: ${today}`);
  return date;
}
```

"Hoy" llega siempre del servidor (`todayInAppTimeZone()`), así que un texto
que no sea una fecha es un error de programación: mejor que falle en voz alta
que dar una llama equivocada. Va aparte para que las dos funciones lo
conviertan igual.

```ts
function daysSinceStrike(lastStrikeDay: Date | null, today: Date): number | null {
  if (!lastStrikeDay) return null;
  return Math.round((today.getTime() - lastStrikeDay.getTime()) / DAY_MS);
}
```

Días de calendario entre el último golpe y hoy: 0 si fue hoy, 1 si fue ayer.
`null` si nunca ha golpeado. Las dos fechas están a las 00:00 UTC, así que la
resta es un múltiplo exacto de un día. `Math.round` es solo por si acaso:
Colombia no tiene horario de verano.

```ts
export type FlameStatus = "lit" | "at-risk" | "out";

export type FlameState = {
  status: FlameStatus;
  days: number;
  extinguished: boolean;
};
```

Lo que necesita la pantalla. `days` es el número que se enseña (la racha, o 0
si está apagada). `extinguished` es la condición del aviso: apagada **y** con
racha guardada mayor que 0.

```ts
export function flameState(flame: number, lastStrikeDay: Date | null, today: string): FlameState {
  const days = daysSinceStrike(lastStrikeDay, parseToday(today));
  if (days !== null && days <= 0) return { status: "lit", days: flame, extinguished: false };
  if (days === 1) return { status: "at-risk", days: flame, extinguished: false };
  return { status: "out", days: 0, extinguished: flame > 0 };
}
```

El estado al leer una página, sin escribir nada:

- golpeó hoy (0 días): encendida, con la racha;
- ayer (1): en peligro, también con la racha (todavía puede salvarla);
- antes de ayer o nunca: apagada, con 0. Si había racha (`flame > 0`) es una
  llama extinguida y sale el aviso; un usuario nuevo (racha 0) no lo ve.

`days <= 0` incluye un día futuro, que no debería existir; si apareciera,
cuenta como hoy en vez de apagar la llama.

```ts
export function flameAfterStrike(
  flame: number,
  lastStrikeDay: Date | null,
  today: string,
): { flame: number; lastStrikeDay: Date } {
  const todayDate = parseToday(today);
  const days = daysSinceStrike(lastStrikeDay, todayDate);
  if (days !== null && days <= 0) return { flame: Math.max(flame, 1), lastStrikeDay: todayDate };
  if (days === 1) return { flame: flame + 1, lastStrikeDay: todayDate };
  return { flame: 1, lastStrikeDay: todayDate };
}
```

Lo que se guarda al asestar un golpe aceptado. El día del último golpe pasa
siempre a hoy. La racha:

- ya golpeó hoy: no cambia, así que dos golpes el mismo día cuentan uno.
  `Math.max(flame, 1)`: si por algún error la racha guardada fuera 0 con el
  día de hoy, al menos queda en 1;
- golpeó ayer: suma 1;
- antes de ayer o nunca: vuelve a empezar en 1.

### `app/mazmorra/batalla/[id]/actions.ts` (modificado)

Función nueva, gemela de `bloquearTarea`:

```ts
async function bloquearUsuario(tx: Prisma.TransactionClient, userId: string) {
  const rows = await tx.$queryRaw<
    { souls: number; level: number; flame: number; lastStrikeDay: Date | null }[]
  >`
    SELECT "souls", "level", "flame", "lastStrikeDay" FROM "User"
    WHERE "id" = ${userId} FOR UPDATE`;
  return rows[0];
}
```

- `tx` es la transacción en curso: todo lo que se haga con ella se confirma
  o se deshace junto.
- `FOR UPDATE` lee la fila **y la bloquea** hasta el final de la transacción:
  otra petición que quiera tocar al mismo usuario espera su turno. Por eso
  después se puede calcular en el código sin miedo a que los valores cambien
  por debajo.
- `$queryRaw` con plantilla (las comillas invertidas): `${userId}` viaja como
  parámetro, nunca pegado al SQL, así que no hay inyección.
- El tipo entre `< >` le dice a TypeScript qué columnas vuelven. Postgres
  devuelve el `TIMESTAMP` como `Date`.

El paso 4 de `asestarGolpe`, antes:

```ts
const updated = await tx.user.update({
  where: { id: user.id },
  data: { souls: { increment: gained } },
  select: { souls: true, level: true },
});
const level = levelForSouls(updated.souls).level;
if (level !== updated.level) {
  await tx.user.update({ where: { id: user.id }, data: { level } });
}
const leveledUp = level > levelForSouls(updated.souls - gained).level;
```

Después:

```ts
const owner = await bloquearUsuario(tx, user.id);
const gained = strikeSouls + (victorySouls ?? 0);
const souls = owner.souls + gained;
const level = levelForSouls(souls).level;
const flame = flameAfterStrike(owner.flame, owner.lastStrikeDay, todayInAppTimeZone(now));
await tx.user.update({
  where: { id: user.id },
  data: {
    souls,
    ...(level !== owner.level && { level }),
    flame: flame.flame,
    lastStrikeDay: flame.lastStrikeDay,
  },
});
const leveledUp = level > levelForSouls(owner.souls).level;
```

- Se bloquea al usuario **el último**, después de la tarea y de la vigilia
  (el orden de siempre, para evitar interbloqueos; ver
  [la sesión de la batalla](2026-10-07-batalla.md)).
- Las almas nuevas se calculan en el código (`owner.souls + gained`) en vez
  de con `increment`: con la fila bloqueada es igual de seguro.
- `todayInAppTimeZone(now)`: el "hoy" de Colombia con la misma hora (`now`)
  con la que se cerró la vigilia.
- `...(level !== owner.level && { level })`: si el nivel cambia, el objeto
  `{ level }` se "esparce" dentro de `data`; si no, `false` no añade nada.
  Así el nivel solo se escribe cuando cambia, pero en la **misma** escritura
  que las almas y la llama.
- `leveledUp` compara con el nivel que daban las almas de antes del golpe.
- Un golpe rechazado (vigilia sin terminar, jefe caído) sale antes del paso 4
  y no toca al usuario. Comenzar una vigilia no toca la llama.

```tsx
const FLAME_COLORS: Record<FlameState["status"], { icon: string; number: string }> = {
  lit: { icon: "text-ember", number: "text-ember" },
  "at-risk": { icon: "text-ember/45", number: "text-ash" },

```

Los colores de cada estado, solo con tokens. `text-ember/45` es el color
`ember` al 45 % de opacidad: el Figma dibuja así la llama en peligro.
`Record<FlameState["status"], …>` obliga a TypeScript a exigir los tres
estados.

```tsx
const FLAME_STATUS_TEXT: Record<FlameState["status"], string> = {
  lit: "Encendida.",
  "at-risk": "En peligro: golpea hoy para mantener la llama.",
  out: "Apagada.",
};
```

Lo que se añade a "Racha: N días." en la etiqueta para el lector de
pantalla.

```tsx
function FlameBadge({ flame }: { flame: FlameState }) {
  const colors = FLAME_COLORS[flame.status];
  const daysText = flame.days === 1 ? "1 día" : `${formatNumber(flame.days)} días`;
  return (
    <p
      role="img"
      aria-label={`Racha: ${daysText}. ${FLAME_STATUS_TEXT[flame.status]}`}
      title={flame.status === "at-risk" ? "Golpea hoy para mantener la llama" : undefined}
      className="flex shrink-0 items-center gap-1 text-[13px] leading-[normal] font-semibold"
    >
      <Flame aria-hidden size={16} className={colors.icon} />
      <span className={colors.number}>{formatNumber(flame.days)}</span>
    </p>
  );
}
```

- `daysText`: singular con 1 ("1 día") y plural en el resto, incluido el 0.
- `role="img"` + `aria-label`: el lector de pantalla trata el bloque como una
  imagen con esa descripción y no lee su contenido por separado.
- `title` solo en peligro: es el texto que aparece al pasar el ratón.
- `shrink-0`: la llama nunca se encoge; si falta sitio, el que se corta es el
  nombre.
- El icono `Flame` de lucide (16 px) es decorativo (`aria-hidden`), porque la
  etiqueta ya lo dice todo. Hereda el color con `currentColor`, así que
  basta con la clase `text-…`.

## Para retomar en otro equipo

1. `git pull` y `npm install` (`postinstall` ejecuta `prisma generate`).
2. No hace falta ninguna variable nueva en `.env`.
3. `npx prisma migrate status` debe decir que la base está al día: la
   migración `20261008214803_llama` ya está aplicada en la base compartida.
4. Para probar sin esperar 25 minutos: `$env:EMBER_TEST_VIGIL_SECONDS='10';
   npm run dev` (PowerShell).
5. Para ver los estados sin esperar días, cambia `lastStrikeDay` y `flame`
   **solo de una cuenta de prueba** (hoy, ayer, antes de ayer o `NULL`), a
   las 00:00 UTC del día que quieras simular.
